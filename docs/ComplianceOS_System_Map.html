PART ONE

Four ways in

The app is a single page with no router. Which surface loads is decided by the URL query string, so these are the only four entry points that exist.

/

Landing page for a signed-out visitor, the full app for a signed-in one.

/cbam-check

Public CBAM checker, no login. Rewrites to ?public=cbam and captures the email as a lead.

?demo

Design system gallery. Bypasses auth entirely — anyone with the link sees it.

/functions/v1/underwriting-signal

Partner API for lenders. Authenticated by a ComplianceOS key, not a login.

PART TWO

The exporter's journey

Six stages in the order they happen. Each one ends in something the exporter can hold — a number, a file, or a message. Stage two is where the product proves itself.

1
First 5 minutes · Exporter

Tell us what you ship and where

Sign up, then onboarding captures the company, IEC, GSTIN, turnover band, product category and target markets. Returning users get a short problem picker instead. Nothing is uploaded yet.

Output A first RoDTEP estimate on the dashboard
2
The proof moment · Exporter or their CA

Import last year's shipping bills

One CSV, in whatever format ICEGATE, the CHA register or Tally already exports. Every HS code is matched against 10,501 rows of DGFT Appendix 4R as amended by Notification 60/2025-26. Duplicate bills are skipped. Nothing is claimed yet.

Output A single ₹ figure of unclaimed RoDTEP
3
Before filing · Exporter reviews, CA verifies

See which rupees are safe to claim

Every rate carries its provenance: an exact match to an 8-digit schedule row, an estimate borrowed from the 6-digit sub-heading, or no match at all. Only the first two reach the claim register. Each bill then moves through unclaimed, filed, credited or rejected.

Output A claim register CSV the CHA files from
4
Per shipment · Exporter

Clear the next shipment without a rejection

The gate check runs risk score, checklist completion, OFAC screening of the buyer and CBAM scope in one pass, and blocks or flags before the goods move. Documents, HS classification and labels are checked here too.

Output A cleared shipment and a bank-ready deal pack
5
Ongoing · Product works while they don't

Stay covered without opening the app

RoDTEP claims lapse one year after the shipping bill; BRC realisation is due at 270 days; EPCG obligations run six years. All three are watched, and a monthly digest reports unclaimed totals, expiring windows and rejected claims.

Output A WhatsApp message on the 1st of each month
6
Second audience · A lender, never the exporter

Let a financier read the compliance score

The exporter issues an API key from Settings and hands it to a bank or a TReDS platform. That partner calls one endpoint and gets back a compliance score, a gate verdict, an FTA duty estimate and CBAM exposure, with no access to the underlying shipments.

Output A JSON financing signal, keyed per exporter

PART FOUR

Fix before the exporter sees it

Six things that will damage trust if they are found rather than disclosed. The first three are the ones a paying customer can hit today.

The Label Checker invents its verdict without an OpenAI key

With no OPENAI_API_KEY set, the vision function returns a fabricated pass/fail for every rule and flags it only as mock: true. The UI logs a console warning and displays the fake result as though it were real. Either set the key or hide the feature — an exporter acting on an invented label verdict is the worst possible failure.

The alerts screen silently falls back to five hardcoded items

When the regulatory_changes table is empty, the app substitutes five curated alerts written into the source and renders them identically to real feed rows — same styling, same source links, no marker. The edge function that does return a live versus fallback label is never called, because the app queries the table directly. A user cannot tell a stale demo from a working feed.

Three finance features return shaped responses, not real ones

TReDS submission, TReDS eligibility and the ECGC premium all produce plausible numbers from hardcoded rules. They look like integrations. Label them "indicative" in the UI before anyone quotes a premium to their bank.

The lender API scores exporters from its own duty table

The underwriting endpoint carries an inline copy of the risk model with MFN rates hardcoded at EU 7.5%, US 5.0%, UK 6.0% and so on, rather than reading the ADB tariff data the app itself uses. A bank and the exporter can therefore see different duty and risk figures for the same shipment, and the two copies drift apart on every edit.

Currency conversion is frozen in the source

USD 84, EUR 91, GBP 107 and AED 23 are constants compiled into the app, and the CBAM carbon price is fixed at €65 per tonne. Any entitlement on a foreign-currency shipping bill drifts as the rupee moves. Fine for an estimate, wrong for a filing.

Two schedules do not match what the code claims

The monthly recovery digest cannot fire: its pg_cron registration is still commented out in the migration, so setting the WhatsApp credentials is not enough. And the feed cron says "every 6 hours" in its own comment while the deploy config runs it once daily at 02:00, with the Supabase project URL hardcoded in the handler rather than read from the environment.
